## 원인 — 끝난 프로그램이 켜 놓고 간 모드를 다음 프로그램이 물려받는다

화면에 찍히던 두 글자는 터미널 **포커스 리포트** `ESC[I`(DECSET 1004) 에서 앞의 ESC 가 빠진 잔해다.
codex 는 ESC 를 "취소" 로 삼키고 남은 두 글자를 평범한 입력으로 받는다.

문제는 **모드의 수명**이었다.

- xterm 은 DEC private mode 를 **패인 수명 내내** 들고 있고, 그걸 켠 프로그램이 끝나도 되돌리지 않는다.
- Claude Code 는 대체 화면(alt-screen)에서 1004 를 **켜고, 끄지 않은 채** 끝난다.
- 그 뒤에 뜬 프로그램은 요청한 적 없는 리포트를 물려받는다.

codex 가 요청한 적이 없다는 건 바이너리로 확인했다. **1004 의 비활성 시퀀스만 있고 활성 시퀀스는 아예 없다** — 켤 수가 없는데 받고 있었다.

```
?1004 : 1 회   →  ESC[?1004l (끄기) 만 존재
?2004 : 4 회   →  bracketed paste 는 켜기·끄기 둘 다 존재
```

리포트가 한 개가 아니라 두 개씩 겹쳐 보인 것은, 창 복귀 한 번에 리포트를 만드는 경로가 **둘**이기 때문이다.
WebView2 가 뒤늦게 주는 진짜 focus 이벤트 하나, 그리고 focus keeper 가 xterm 의 포커스 상태를 되살리려고 쏘는 **가짜** focus 이벤트 하나다.
후자는 `app.js` 주석에 이미 "DECSET-1004 report exactly the same" 이라고 적혀 있던, 알고 쏘던 쪽이다.

## 수정

`crates/mycli-desktop/frontend/app.js` — 프런트엔드 전용, +52 줄.

1. **셸이 패인을 되찾으면 남은 1004 를 되돌린다.** `markPaneReturnedToShell()`(OSC 133;D) 에서 xterm 자신의 파서로 비활성 시퀀스를 먹인다. 다른 DEC 모드는 건드리지 않는다.
2. **대체 화면 이탈도 같은 신호로 쓴다.** OSC 133 마크가 없는 원격 셸(ssh)에서 vim·htop 류가 끝난 경우를 덮는다. 대체 화면에 **들어갈** 때는 아무것도 하지 않는다.
3. **focus keeper 의 가짜 focus 이벤트는 리포트를 만들지 않게 막는다.** OS 포커스가 바뀐 적이 없고, 뒤따르는 진짜 이벤트가 이미 하나를 보낸다.

## 검증 방법과 한계

cargo 빌드 없이 **실제 `app.js` 를 그대로 부팅**시키고(Tauri IPC 스텁 하네스), PTY 로 나가는 바이트를 전부 기록해 셌다. 변경 전 코드와 변경 후 코드를 각각 **별도 포트**에 띄워 같은 스크립트로 측정했다.

- 캡처 왼쪽의 탐색기 오류와 빈 패널은 하네스 스텁의 한계다. 이 이슈와 무관하다.
- ⑤ WebView2 의 진짜 focus 는 헤드리스 브라우저가 OS 포커스를 갖지 못해 재현할 수 없었다. 다만 진짜 이벤트와 가짜 이벤트는 xterm 의 **같은 핸들러**(`_handleTextAreaFocus`)를 타므로, ⑥ 에서 리포트가 나가는 것이 그 경로가 살아 있다는 확인이 된다.
- **실기 확인은 남아 있다.** 실제 Claude Code 세션에서 codex 세션으로 오갔을 때 더는 찍히지 않는지는 사용자 환경에서 봐야 한다.
