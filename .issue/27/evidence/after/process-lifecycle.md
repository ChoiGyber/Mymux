# after — 창을 닫으면 프로세스도 끝난다

빌드: `fix/27-exit-on-main-window-close` (main 창 `Destroyed` 에서 `handle.exit(0)`)
조건은 before 와 동일 — 새 WebView2 프로필, CDP 로 `closeAppWindow.destroy()`.

## 1. 종료 — 오버레이를 띄운 채로 닫아도 끝난다

before 보다 엄격한 조건으로 확인했다. `buddy_overlay_show` 로 데스크톱 캐릭터를 띄워
`buddy-overlay` 창이 **보이는 상태**에서 main 창을 닫았다.

```text
닫기 전
   Id Path
   -- ----
20044 D:\Project\Mymux\target\debug\Mymux.exe          ← 테스트 인스턴스
21236 C:\Users\ChoiGyber\AppData\Local\Mymux\Mymux.exe  ← 사용자 설치본 (건드리지 않음)

닫은 뒤 (5초)
   Id Path
   -- ----
21236 C:\Users\ChoiGyber\AppData\Local\Mymux\Mymux.exe
```

**테스트 인스턴스가 사라졌다.** before 에서는 같은 자리에 그대로 남아 있었다.

연속 실행 시나리오에서도 확인 — 닫은 직후 테스트 인스턴스 개수:

```text
0
```

## 2. 오버레이 회귀 없음

`buddy_overlay_show` → `buddy_overlay_hide` → 다시 `show` 를 CDP 로 호출하고, 오버레이 창의
DOM 을 직접 읽었다.

```json
{"cls":"show","char":"mascot","text":"'테스트 세션' 작업 다 끝났슈! 🎉"}
```

창이 뜨고, 마스코트 캐릭터와 충청도 사투리 말풍선이 정상 렌더링된다. `hide` 도 정상 응답했다.
이 수정은 오버레이를 없애지 않고 **앱이 끝날 때 같이 정리되게** 할 뿐이다.

## 3. 창 크기 저장·복원 회귀 없음 (#25 기능)

| 단계 | 앱이 인식한 크기(CSS px) | 실제 창(물리) | 저장값 |
| --- | --- | --- | --- |
| 첫 실행 | 1280 × 800 | — | — |
| 1400×900 으로 변경 | 1387 × 863 | 1734 × 1117 | — |
| 닫음 | — | — | `1732 × 1078 @ 63,50` |
| 재실행 | **1387 × 863 (복원)** | 1734 × 1117 @ 71,50 | — |

## 4. 연속 실행 — 최신 값이 남는다

이 이슈의 2차 피해(좀비가 낡은 값으로 덮어쓰는 것)가 사라졌는지 확인했다.

```text
실행 A: 1400×900 으로 닫음  → 저장 {width:1732, height:1078, x:63,  y:50}
실행 B: 1200×760 으로 닫음  → 저장 {width:1482, height:903,  x:125, y:88, prev_x:63, prev_y:50}
```

B 의 값이 그대로 남고 A 가 되살아나지 않는다. 각 실행이 자기 차례에 완전히 종료되므로
**낡은 캐시를 들고 있는 프로세스 자체가 존재하지 않는다.**

로그오프로 좀비를 깨우는 원래 시나리오는 재현하지 않았다. 좀비가 생기지 않는다는 것이
확인되면 그 시나리오는 성립할 수 없다.

## 검증 중 있었던 오탐 하나

중간에 저장값이 기본 크기(1600×1000 = 1280×800 의 물리 픽셀)로 남은 적이 있었다.
**코드 결함이 아니라 검증 타이밍 문제였다** — 리사이즈 직후 앱이 `Resized` 를 처리하기 전에
창을 닫아서, 캐시에 새 크기가 들어가기 전의 값이 저장된 것이다. 리사이즈 후 CDP 로 앱이
인식한 크기를 확인하고 나서 닫도록 절차를 고치자 정상으로 나왔다. 위 표의 수치가 그 결과다.

# 코드 리뷰 대응으로 추가된 검증

리뷰가 `REQUEST_CHANGES` 를 내며 두 가지를 짚었고, 둘 다 반영했다.

## 5. 실제 X 버튼 경로 완주 (증거 공백 메우기)

리뷰 지적: 위의 검증은 CDP `closeAppWindow.destroy()` 로 닫았는데, 그 경로는
`WindowMessage::Destroy` 로 직행하며 **`CloseRequested` 를 내지 않는다.** 그래서 창 상태
플러그인의 실측 지오메트리 캡처 핸들러가 테스트 중 한 번도 돌지 않았다. 종료 메커니즘은
입증됐지만 지오메트리 캡처는 미입증이었다.

WM_CLOSE(0x0010)를 실제로 보내 사용자가 X 를 누르는 경로를 그대로 재현했다.

```text
1. 창을 1500×950 @ 80,60 으로 조정 (앱 인식: 1486×914)
2. WM_CLOSE 전송        → 종료 모달이 뜸
                          {"hidden":false,"html":"Quit Remember the open sessions and restore them next time?"}
                          ← CloseRequested 가 실제로 발생했다는 증거
3. 모달의 '저장하고 종료' 클릭
4. 결과
   프로세스            0개
   .window-state.json  {"width":1857,"height":1141,"x":100,"y":75,...}
   session.json        해시 변경 확인 (탭 1개 "Terminal" = 테스트 세션)
```

**세 가지가 한 번에 확인됐다** — `CloseRequested` 를 거친 지오메트리 저장, 세션 저장,
그리고 프로세스 종료. 테스트에 쓴 세션 파일은 백업에서 원래대로 복원했다.

## 6. 업데이트 설치 중에는 종료하지 않는다

리뷰가 막은 유일한 항목이다. 이 변경은 **없던 실패 경로를 새로 만든다.**

수정 전에는 프로세스가 죽지 않아 `update_install` 이 항상 끝까지 돌았다. 수정 후에는 설치
도중 창을 닫으면 프로세스가 즉시 끝난다. 다운로드는 수십 MB 라 수십 초짜리 창이고, 그 사이
닫기를 막는 코드가 없다.

| 플랫폼 | 피해 |
| --- | --- |
| Windows | 무해 — 인스톨러를 `ShellExecuteW` 로 띄운 뒤 스스로 종료하므로 임시 파일만 남는다 |
| Linux AppImage | **복구 불가** — 실행 중인 이미지를 `rename` 으로 치운 뒤(`tauri-plugin-updater:1004`) 새 바이트를 `write` 하므로(`:1033`), 그 사이에 죽으면 설치 경로에 실행 파일이 없다. 되돌리기 코드는 `Err` 분기에만 있어 강제 종료에는 걸리지 않는다 |

반영: `update.rs` 에 설치 진행 플래그를 두고 종료 훅이 확인한다. 설치가 실패하면 플래그를
내리고, 그때 창이 이미 닫혀 있으면 `update_install` 이 대신 프로세스를 끝내 창 없는 프로세스가
남지 않게 한다.

**이 게이트는 실기로 검증하지 않았다.** 현재 버전이 최신이라 `update_install` 이 조기 반환하므로
설치 경로를 태울 수 없다. 코드 경로 검토로 갈음하고, 게이트 추가 후에도 정상 종료가 되는 것은
위 5번에서 확인했다.

## 정정 — 이 리포트의 초안이 틀렸던 부분

초안에는 "`destroy()` 는 `send_user_message` 라 재진입 위험이 있고 `exit` 은 프록시라 안전하다"고
적었다. **사실이 아니다.** `destroy()` 도 같은 프록시 경로를 쓴다(`tauri-runtime-wry:2283-2290`).

`exit(0)` 이 여전히 나은 선택인 이유는 다르다 — 오버레이를 없애는 것은 "지금 다른 창이 없다"는
우연에 기대는 방식이라, 나중에 창이 하나만 더 생겨도 이 버그가 조용히 되살아난다. 코드 선택은
바뀌지 않았고 근거만 바로잡았다.
