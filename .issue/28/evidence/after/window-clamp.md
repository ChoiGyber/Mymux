# after — 첫 실행 창이 작업영역에 맞춰 줄어든다

빌드: `feat/28-clamp-window-and-drop-acl`
계측 조건은 before 와 동일 — `tauri.conf.json` 기본값을 임시로 4000×3000 으로 두고 실행.
(임시 변경은 계측 후 되돌렸다. 커밋에는 원래 값 1280×800 만 들어간다.)

## 결과

| | before | after |
| --- | --- | --- |
| 요청한 기본 크기 | 4000 × 3000 (논리) | 4000 × 3000 (논리) |
| 실제 창 (물리) | 2566 × 1614 | **2544 × 1532** |
| 논리 환산 | 2053 × 1291 | **2035 × 1226** |
| 작업영역 (논리) | 2048 × 1232 | 2048 × 1232 |
| 판정 | 폭 +5, 높이 +59 **초과** | **안에 들어감** |

## 검증 중 잡은 실제 결함 — 프레임 보정

첫 구현은 클램프가 걸리긴 했지만 여전히 작업영역을 39px 정도 넘었다. 원인은 단위가 아니라
**두 API 의 기준이 다른 것**이었다.

```text
win.outer_size()   창 전체 (프레임 포함)
win.set_size(..)   → tauri-runtime-wry:3527 에서 window.set_inner_size(..)
                     즉 inner (프레임 제외)
```

outer 로 재서 그 값을 그대로 `set_size` 에 넘기면 프레임만큼 초과한다. 판정은 outer 기준으로 하되
설정값은 `outer - inner` 를 빼서 환산하도록 고쳤다. 위 표의 after 수치가 그 결과다.

**과대 기본값으로 실측하지 않았다면 그냥 넘어갔을 결함이다.**

## 기본값(1280×800)에서는 아무 일도 하지 않는다

이 PC 작업영역이 2048×1232 이라 기본 창은 넘치지 않는다. 클램프는 `outer <= max` 면 즉시 반환하므로
정상 환경에서는 창을 건드리지 않는다.

## 복원된 창은 건드리지 않는다

저장된 상태가 있으면 창 상태 플러그인이 이미 모니터 교차 검사를 거쳐 복원한 뒤다. 거기에 덧칠하면
사용자가 의도한 크기를 빼앗게 되므로, 상태 파일(`DEFAULT_FILENAME`) 존재 여부로 첫 실행만 가려낸다.

## ACL 권한 제거

`capabilities/default.json` 에서 `"window-state:default"` 를 뺐다. 프런트엔드는 이 API 를 전혀
쓰지 않고(`frontend/app.js` 에서 `windowState`/`restoreState`/`saveWindowState`/`window-state`
검색 0건), 저장·복원은 전부 Rust 내부 경로라 ACL 을 거치지 않는다.

권한을 뺀 뒤에도 저장·복원이 그대로 동작하는 것은 아래 절에서 확인한다.

## 검증 결과

| 항목 | 결과 |
| --- | --- |
| 과대 기본값(4000×3000) 클램프 | 통과 — 논리 2035×1226, 작업영역 2048×1232 안 |

# 코드 리뷰 대응 (REQUEST_CHANGES → 수정 반영)

리뷰가 major 2건을 냈고 둘 다 타당해 고쳤다.

## M1 — 위치를 한쪽 끝만 클램프하고 있었다

`monitor_work_area` 가 크기 `(w, h)` 만 돌려주고 작업영역의 **원점** `rcWork.left/top` 을 버렸다.
그래서 재배치를 `pos.x.max(0)` 로밖에 못 했는데, 이건 음의 방향만 잡고 오른쪽·아래를 놓친다.

크기 계산이 정확해서 결과 창이 **정확히 작업영역 크기**가 되는 것이 문제를 키웠다. 그런 창은
좌상단이 정확히 `(work.left, work.top)` 일 때만 화면에 들어온다. 게다가 **리사이즈는 창을 옮기지
않는다** — tao 가 `SWP_NOMOVE` 를 쓴다(`tao-0.35.3 .../util.rs:113`).

깨지던 경우 셋:

1. **양수 오프셋** — tao 는 위치를 안 주면 `CW_USEDEFAULT` 를 쓰고 Windows 가 캐스케이드로 배치한다.
   `(30, 30)` 에 놓인 창은 축소 후에도 30px 삐져나간다. **이 이슈가 고치려던 바로 그 증상이다.**
2. **작업표시줄이 위/왼쪽** — `work.left/top` 이 0 이 아닌데 `max(0)` 이 창을 그 밑으로 밀어 넣는다.
3. **멀티모니터** — 주 모니터 왼쪽의 보조 모니터에 있으면 `pos.x` 가 음수이고, `max(0)` 이 창을
   주 모니터 `(0,0)` 으로 순간이동시킨다. 크기는 보조 모니터 기준으로 계산했는데 착지는 다른 곳이다.

수정: 원점까지 반환하고 양쪽 끝을 클램프한다. 리사이즈 후 크기를 다시 읽어 계산한다.

```rust
pos.x.clamp(work_x, far_x.max(work_x))   // far_x = work_x + max_w - placed.width
```

### 검증 — 물리 픽셀 기준

```text
작업영역   2560 × 1540 at (0,0)
창         2544 × 1532 at (8,0)
창 오른쪽 끝  2552  ≤ 2560
창 아래 끝    1532  ≤ 1540
PASS: 창이 작업영역 안에 완전히 들어감
```

창이 `(8,0)` 오프셋에 놓였는데도 경계 안이다. 수정 전이라면 크기가 작업영역과 같아 8px 남았을 상황이다.

## M2 — 주석이 사실과 달랐다

"저장된 상태가 있으면 플러그인이 이미 모니터 기준으로 검증했다"고 단언했는데 **사실이 아니다.**

`tauri-plugin-window-state-2.4.1/src/lib.rs:213-218` 은 복원 **크기를 모니터 검사 없이 무조건**
적용한다. 모니터를 보는 곳은 POSITION 뿐이고, 그것도 `intersects` — "맞는지"가 아니라 "1픽셀이라도
겹치는지"다.

즉 4K 에서 저장한 크기를 1366×768 노트북에서 복원하면 과대 크기가 그대로 들어오고, 이 클램프는
거짓 전제 위에서 건너뛰고 있었다.

**동작은 그대로 두고 주석만 고쳤다.** 복원된 크기를 건드리지 않는 것은 여전히 옳지만, 그 근거는
"플러그인이 처리했다"가 아니라 **"사용자가 고른 크기를 overrule 하지 않는다"는 스코프 결정**이다.

→ **"큰 화면에서 저장한 크기가 작은 화면에서 넘친다"는 별개 문제로 남는다.** 후속 이슈감.

## 리뷰가 소스로 확인해 준 것

Win32 구현(hwnd 캐스팅, `cbSize`, null 검사, unsafe 경계), **좌표계 일관성**(tao 가 PMv2 를 켜므로
`rcWork` 와 `outer_size()` 가 같은 물리 픽셀 — 혼합 DPI 에서도 크기 비교가 어긋나지 않는다),
**프레임 보정이 근사가 아니라 대수적으로 정확**(결과 outer = `min(outer, max)`), 호출 시점(플러그인
복원이 먼저, 클램프가 나중), ACL 제거 안전성(프런트엔드 검색 0건 재확인, Rust 경로가 IPC 를 넘지 않음).
